# UI patterns

The detailed design rules for each part of the Seshboard UI. [.claude/rules/ui.md](../.claude/rules/ui.md) has the rules every UI change follows (tokens, type scale, status colours, buttons, components) and an index of this page. Read the section for the area you change; when a new view needs a pattern that is not here, add it in the same change.

## Components

Use `Button`, `Kbd`, `Pill` and `Meter` from `components/ui/` instead of writing these class strings by hand; `npm run check` fails on `btn-secondary` or a raw `<kbd>` elsewhere. `Button` variants: `primary` for the one yellow action in an area, `secondary` (the default) for Cancel, Close and Choose…, `quiet` for toolbar icons and inline controls (`selected` for an open panel or the current view), `danger` for deleting or reverting (`filled` only for the confirm button of a destructive dialog), `side` for the Ask panel's blue, and `tint`, a blue tint without an edge, for an offer next to a row's quiet buttons that isn't the area's main action (Update on another computer's row in Settings › Remote). Sizes are `sm` (24px), `md` (28px, toolbars and dialogs) and `lg` (32px, cards, the message box, a view's main action). Pass `shortcut="<registry id>"` (or `kbd="⌘↵"` for a dialog's own key) to show the shortcut and announce it, and `iconOnly` with an `aria-label` for an icon button (the label becomes its tooltip). `Kbd` shows a shortcut on its own, as glyphs, a stored `cmd+enter` or a registry `shortcut`; its `on-accent` tone is for inside a yellow button, `plain` drops the keycap and `cap` is one key on a 20px keycap. `KeyCombo` draws a shortcut's alternatives as keycaps, one per key, with "or", "then" and "to" between them and the keys spoken as words for screen readers. `Pill` is the small rounded chip above the message box (project actions, the task strip, background tasks with `tone="ok"`, `ghost` for "Add action", `dashed` for Add step in an editor, `error` for something that failed such as a catch-up's failing tests), and `CountBadge` is the count next to a group heading. `Meter` draws anything that fills up, as a bar or a ring, in the level colours; give it a `label` unless the control around it already says the number. `SplitButton` is a button with a ▾ beside it for related ways to do the same thing (New session's Start: Start session, Add to queue, Start in a new worktree), one shape with a 1px line between the halves; the main action's shortcut stays on the main part, the menu opens above, and a reason that only stops the main action leaves the ▾ usable. `Dialog` is the shell of every modal: scrim, panel on the overlay surface, header with `title`, optional `subtitle` and a close button, a scrolling body, and a footer (`footer` on the right for Cancel and the primary action, `footerStart` on the left for Delete or a status line). Widths are `sm` (420px, confirmations), `md` (560px), `palette` (640px, the command palette; `palette-wide`, 680px, for its prompt step), `sheet` (880px, the shortcuts sheet), `lg` (900px) and `full` (1200px wide and 88% of the window tall, for a file preview with an iframe that fills it); `placement="top"` keeps dialogs whose height changes as you type from jumping, `flush` drops the body padding for lists and panes, and `bare` drops the header for a search field (the `title` still names the dialog). It closes on Escape and on a click on the scrim (`dismissable={false}` to stop that), calls `onSubmit` on ⌘↵, and only the dialog on top reacts; a child that takes Escape itself (a shortcut recorder, a dropdown) marks the key handled with `preventDefault()`. Use `ConfirmDialog` for a yes or no question (`details` for a breakdown under its text, `start` for a "Review first" on the left of the footer). `Stepper` is a whole number with − and + (the archive days): it can be typed too, and its `hook` gives the group and its parts `data-` hooks. `Checkbox` takes `checked="mixed"` for a group whose rows are only partly picked. `SegmentedControl` puts related choices in one track: `mode="radio"` for one value (arrow keys move and choose, one Tab stop), `mode="toggle"` for independent switches such as Changes | Terminal; each segment takes `label`, `icon`/`iconOnly`, `badge`, `dot`, `tooltip`, `kbd` and `data` hooks; `fill` makes the track as wide as its container with the segments sharing it (the sidebar's Recent | Quickest to unblock), and `quiet` drops the track for icon buttons in a header (the session's panels). Choices that need a description under them stay `RadioGroup` cards. `Notice` is a tinted box without a border: `tone` `neutral` (the default, a quiet grey box for a note or an empty state), `info` (blue, for something worth reading that sits on a card or among settings), `accent` (a limit you reached), `caution` (something turned off outside Seshboard that stops a feature, such as notifications blocked in the system's settings), `warn`, `error` (announced at once) or `success`, with an `icon`, `actions` (small Buttons) and `onDismiss`; `inline` makes it one quiet line without a box. Plain errors under a field stay text. `SectionHeader` is the small capitals over a group of rows, with `tone` (`neutral`, `needs-you`, `working`), a `count`, an `action` (Select all) and `toggle` for a collapsible group; `as="h2"` or `"h3"` when a section points at it with `aria-labelledby`. `className` is for layout (`ml-auto`, `w-full`, `min-w-0`); to change a component's look, change the component. `npm run check` also fails on a hand-written dialog scrim (`bg-scrim`) or `role="radiogroup"` outside `components/ui/`.

`WorkingPanel` (`components/ui/`) is the working mark: the app icon's patch panel at 16px (`size`), its five free jacks lighting up in turn. Use it wherever something says Claude is working, next to a label that says what is happening (it is `aria-hidden`). `state` is `working` (the light moves), `still` (all five softly lit, for Compacting) or `waiting` (all five in `warn`, for Waiting for you). Reduce motion shows the still frame. Its order, round time and tail come from `@seshboard/protocol/working-panel`, which the Dock's animation (`dockActivity.ts`) reads too, so the two stay in step. Its colours are the `working-*` tokens, so it follows the theme: the holes step from the canvas, the light is generated from the accent (Demo Time keeps the icon's amber), and the themes named after an icon colourway set that colourway's plug colours. The phone has a copy (`apps/remote/src/components/WorkingPanel.tsx`), which a test keeps the same.

## Surfaces and lines

A session screen splits by surface, not by line. The only border on it is the message box's.

1. **Surfaces, not lines.** Two tones split the window. The sidebar and the side panels (Changes, Why, Ask, Agents, Commands, a file preview, a mod's pane) use the darker `bg-sidebar`; the conversation uses the lighter `bg-bg`. Don't put a border where two surfaces meet. A diff in the Changes panel sits on `bg-bg`, inset with 4px margins and a 6px radius, since `code-bg` is the sidebar's own colour in dark mode.
2. **A line only when content scrolls under.** A fixed header or footer gets a hairline only while content scrolls beneath it. `useScrollEdge(scrollRef)` (`components/ui/`) gives `{ atTop, atBottom }` and re-renders only when one flips. Put `edge-b` on a header with `data-scrolled={!atTop || undefined}`, and `edge-t` on a footer with `data-scrolled={!atBottom || undefined}`. The line fades in over 120ms (at once with Reduce motion). Session, remote session, computer, run and project headers share `PANE_HEADER` (`components/ui/paneHeader.ts`). Over the message box there is no line: a 32px `composer-fade` lets the conversation fade out under it, and `composer-fade-room` ends the conversation with as much room, so its last line (Working) clears the fade at the end.
3. **Lists use hover, not dividers.** Rows get `hover:bg-border/45` and `bg-selected` when picked or open, with a 6px radius and 4px side margins, like the sidebar's rows (Changes' file rows). Tints that mean something stay (a file outside the plan keeps `bg-caution/10`).
4. **Cards are tinted, not outlined.** `Notice`, the catch-up card and the tray under the message box use a tint without a border: a tone, or a grey from the text colour (`bg-text/6`), since `bg-card` is the background's own white in light mode. A card that floats over the conversation (the catch-up) adds `shadow-overlay`. The message box keeps its border, since it's where you type, and so do cards that hold a decision (a permission or a question).
5. **Buttons without boxes,** except the main action on screen (Commit, Send, Queue). The session header's panel toggles are `SegmentedControl` with `quiet`: icon buttons without a track, the open one on `bg-selected` with its count. A pill that adds something beside the message box is `Pill ghost` (Add action), faint until the composer area is hovered or focused.

Lines that show focus or selection (focus rings, a tab's underline, a status rail) are not part of this. Windows high contrast (`forced-colors: active`) drops backgrounds, so there the borders come back: `forced-colors:border-l` (or `-r`, `-t`) on a surface that meets another, and `edge-b`/`edge-t` draw a solid line. In light mode the two surfaces have to stay apart without borders; if a theme's `sidebar` is too close to its `bg`, change the theme's token, not the layout (Demo Time's light sidebar can't get darker without taking `faint`, `ok` and `accent-ink` text on it below 4.5:1). Smoke hooks: `data-scrolled` on `data-session-header`, `data-changes-header`, `data-changes-footer` and `data-sidebar-bottom`; `data-composer-area`, `data-composer-fade`.

## The message box and its tray

The message box is two pieces that read as one. **The box** (`Composer`) holds the message and what acts on it. **The tray** (`ComposerTray`) hangs under it and holds how the next message runs.

- **The box** is `max-w-4xl`, the catch-up card's width, a size wider than the conversation (`max-w-3xl`). It has an 18px radius and is at least 3 lines tall, growing to 10 before it scrolls. New session's `large` box keeps its taller text at the same width. The row under the text has, on the left, the attach buttons (image, add context, and @, which opens the file and session list). On the right: mods' chips and the blanks left, then Ask, then Send. While Claude works: Ask, Stop (Esc) and Queue with its menu. Under 600px (`@container/box`), Ask shows only its icon. There is no hint line: the placeholder says it ("Message Claude", or while working "Message Claude. It waits in Up next, or ⌘⇧↩ sends it now.", from `boxPlaceholder` in `composer/trayFold.ts`), and the keys stay in the screen reader hint.
- **The tray** is 16px narrower on each side than the box, with no top border and 12px rounded bottom corners, on `bg-card/55` (one step darker than the box). It is a `group` named "Options for the next message", after the box in the tab order. Left: the chip row (`ComposerChipRow`: profile, model, effort, mode). Right, in this order: Tools (for a session that has it), usage (plan usage and cost, or a Copilot profile's premium requests), and the context ring. It replaces the session footer. With the terminal open below, the right side is only the ring, with every number in its tooltip (`ContextMeter compact`). Sessions, Copilot sessions, New session and run rows all use it; New session's route tray stays on top of its box.
- **Its menus** open below the chip when there is room (New session, with the box mid-screen) and above it otherwise (a session, with the box at the bottom): `ChoiceMenu`'s `placement="auto"`, never pinned.
- **Smoke hooks:** `data-composer-card`, `data-composer-tray`, `data-composer-tray-folded`, `data-composer-tray-info`, `data-folded-chip`.

### Message box chips

The chips on the tray are quiet buttons without borders until hover, and show only the value, with the full meaning ("Effort: Medium") in their label and tooltip. When the row runs out of room it steps through fixed levels (`footerLevel` in `composer/chipFaces.ts`: effort and mode icon-only, then the model without its version, then the profile dot-only) and never truncates a chip. At the last level Auto's model chip also drops the word "Auto" (its wand stays).

When even the smallest level and the right side don't fit, the tray folds (`trayFolds` in `composer/trayFold.ts`, read by the row through `TrayContext`). The profile stays a chip of its own. Model, effort and mode become one chip, "Opus 5.5 · High · Ask first ▾", named with every value ("Model, effort and mode: Opus 5.5, High, Ask first"). Its menu (`FoldedChip`) has a row each for Model, Effort and Mode, each opening its list in place, then Tools and usage, which leave the tray. The context ring stays. The decision measures the row at its smallest level, never the level it shows, and keeps what folds laid out out of sight, so the tray never flips between the two layouts as you type.

## Pasted text

A long paste (`isLongPaste` in `composer/contextItems.ts`) becomes a `paste` context item rather than text in the box, shown in the context tray as a card (`PastedCard` in `ContextTray.tsx`): its first lines in `text-meta` mono, a small "Pasted" label, and edit and remove on hover or focus; a click opens `PastedTextDialog`. Anything that sends from a message box checks `tooLongReason` first (`MAX_PROMPT_LENGTH` in the protocol), so a long message gets a plain reason instead of the engine's "Invalid params".

## A message back in the box

Anything that puts a sent or queued message back in the message box (Edit in Up next, Undo after Remove, and any new path like it) restores what it had as it was written: images as attachments and files as chips, never as `@path` text. A sent message only keeps the prompt, where `promptWithContext` (`composer/contextItems.ts`) wrote the chips as a line of `@` mentions, so run it through `contextFromPrompt` and add the files to the draft's context (see `backInBox` in `TranscriptView.tsx`).

## Ask about this session

Questions about a session (the **Ask** button next to Send, `/btw`, `components/ask/`, state in `state/ask.ts` and `state/askStore.ts`) are never part of the conversation, and their colour is the side channel's blue, `link`, never the accent: the **Ask** button (`Button variant="side"`, outlined; `selected` while the panel is open, a `link` dot with a `ring-card` when an answer came in while it was closed), the `/btw` token in the message box (`bg-link/12 text-link`) and the box's frame (`border-link`), the panel's field (`border-link/45`) and its round send button (`variant="side" filled round`). The panel sits on the right like Changes (380px, its width per window and the front tab per session in `state/rightPanelStore.ts`); with both open they are tabs (`RightPanelTabs`), and anything that opens Changes goes through `toggleChangesPanel` (`state/changesPanelStore.ts`, open per session like Ask, Agents and Commands, so each split pane keeps its own panels), which brings it to the front and never closes Ask. The engine answers from a short-lived fork of the session (`HostManager.askAbout`: `resume` + `forkSession` + `persistSession: false`, spike 14), not `Query.askSideQuestion`, which has no tools, doesn't stream and reports no tokens: the fork keeps the session's tools so the prompt cache matches, and a PreToolUse hook (`isReadOnlyTool`) lets only Read, Grep, Glob and `git status|diff|log|show` through. Threads live in `ask_threads` and `side_questions` (the last 20 per session), and their tokens in `side_question_usage`, shown in Usage as the Side questions row. Nothing about them may change the transcript, Up next, the session's status, title, unread state or notifications.

## Catch-up

The briefing on a session's last finished turn (`components/catchUp/`, logic in `catchUpModel.ts`, cards from the engine's `catchUp/` through `catchup.*`). It is a banner over the conversation (`rounded-[14px]`, card surface, the overlay shadow), or a 40px strip once read; status colours come from `NEED_TONE` and `stateLabel`, never hand-picked. Its keys (`catchup.*` in the registry, `where: 'view'`) never fire in the message box, a field or under an overlay (`catchUpKey`), and Esc closes the nearest thing first (`escapeStep`). A waiting session shows no catch-up: the permission card asks, and its **Why?** opens `WhyPanel` (`catchup.why`, the `useWhy` store) beside the conversation, in the Changes panel's place; Esc closes it before it denies. The engine still makes a card while a session waits, for the sidebar's review times only. Signals come from tool calls and git only; Haiku never sees file contents, diffs or memory (`summaryInput`, `whyInput`), and the smoke run and the screenshots use `stubAnswer`. "Write catch-up summaries with Haiku" turns all of it on and off: off, no banner and no Haiku call.

## Reading mode

(`components/readMode/`, state in `state/readModeStore.ts`, what a reply is in `transcript/readReply.ts`). One reply full window, drawn by a portal from `TranscriptView` (so it has the session view's providers and the session stays mounted under it; the sidebar and the view are `inert` while it is open). It is the one place outside the type scale: the reader picks the text size (`READ_SIZES`, 15.5 to 21.5px, in `readPrefs.ts`), the font and the column width, and the headings, code and tables inside it are in `em` of that size (the `reading` variant of `Markdown`, not a second renderer), because long text wants more room than the 13.5px of the conversation. Its colours are the `paper` and `paper-text` tokens (a warm off-white in light, the same as `bg` and `text` in dark), never `bg`. Tool calls are folded into one line unless shown. The top bar is the window's drag region (room for the traffic lights), Esc closes it before anything behind gets the key (so it never stops Claude), unless a dialog or menu is open. Ways in: the Read button on a turn's last reply (`ReadButton` in `messageActions.tsx`, fed by `readable` on `MessageActions`; shown with the row like the other actions), `read.toggle` (handled in `useSessionShortcuts`, so a pop-out has it) and the palette's Read the last reply. Leaving puts the session back as it was, or scrolls to the reply the reader moved to, and focuses that reply's Read button (else the message box). Another computer's session (`RemoteSessionView`) opens it too, keyed by its row id, with `remote`: its text is `RemoteText`, its tool calls are one line each that open, Reply with quote goes to that session's message box, and Ask about this to that computer.

## Sidebar states

The sidebar is open, minimal (an 80px rail, wide enough for the traffic lights) or closed (`state/sidebarStore.ts`; snapping and keyboard steps are pure helpers in `state/sidebarWidth.ts`). The rail, ⌃⇥ / ⌘⇧U and ⌘P all list sessions through `sidebarGroups` (`state/sidebarOrder.ts`), so their order never differs from the open sidebar's; anything new that walks sessions uses it too. A session row's context menu comes from `useSessionMenu`, shared by both lists. Every view's header starts with `SidebarToggle`, which also makes room for the traffic lights and shows the needs-you pill while the sidebar is closed (in split view only the left pane has it). Rows in the rail use the tooltip's card form (`data-tooltip-title`, `-meta`, `-status`, `-tone`, `-hint`) with `data-tooltip-placement="right"`; use the same for anything else that only shows an icon in a narrow column. A short confirmation of where a keyboard jump landed is the `SessionHud` (top centre, 1.2s, a polite live region), not a toast.

## Split view

The panes are a tiling layout: a tree in the sessions store (`layout`, with `selectedId` the active pane's session and `paneIds` the open ones in reading order). A leaf is a pane showing one session (a session is open once); a split has a direction (`row`: side by side, `column`: stacked), ordered children and `sizes` that add up to 1, and is always normal (two or more children, never a split of its own direction inside it). Every operation is a pure function with tests next to it: the tree in `state/tiling.ts` (split, remove, swap, move, flip, sizes), the geometry in `state/tilingGeometry.ts` (rectangles, minimum sizes, `fits`, dividers, neighbours, drop zones, `planOpen`) and what people do to the panes and the active one in `state/paneState.ts`, which the store applies. A pane is at least `MIN_PANE_WIDTH` x `MIN_PANE_HEIGHT` (340px): ⌥-click splits the active pane (`planOpen`: a pane at least as wide as tall gets the session on its right, a taller one below, the other way when that doesn't fit), and anything that would not fit (opening, dropping, turning a split) is refused with a toast; the area's size comes from `useTilingArea`. **Never remount a session on a layout change** (`SplitPanes`, `components/split/`): `computeLayout` gives each pane's rectangle and the panes are a flat list in a fixed order (by session id, `stableOrder`), absolutely positioned with percentages, keyed by session. A nested render that follows the tree would remount on every change of structure, and moving a DOM element resets its scroll and focus, so neither is used; the smoke step marks each pane and checks it after every change. Dividers (`PaneDivider`) are `role="separator"` between neighbours: drag, arrow keys (24px, Home and End to the minimums), double-click for equal sizes; sizes held to the minimums are only applied for display (`constrain`). When the window is too small for the tree, only the active pane shows (the others stay mounted, hidden, and come back). Dragging (`useTileDrag`, pointer events so it works over terminals and leaves the message box's file drop alone, and the headers' app region is switched off while it runs) works from a pane's `data-pane-handle` header and from a session's sidebar or rail row, over the whole area: a band along each window edge (`edgeBand`, `dropAt` checks it first) docks across the whole window (`dockAtEdge`), otherwise the pane under the pointer has five zones (an edge docks beside it, the centre swaps, or replaces for a session that isn't open). A session that is already open only ever moves (`planDrop` in `paneState.ts` says what a drop does, nothing, or refuses for lack of room); the frame shows where the tile ends up in the layout the drop makes, a red one says it doesn't fit, Esc cancels. Sizes follow VS Code's "auto": when the siblings were all equal everyone is equal again after an add or a remove, otherwise the new pane halves its target and a removed pane's space goes to the neighbour before it (`splitLeaf`, `removeLeaf`, `areDistributed`). The handle must be `no-drag` (the header is the window's drag region, which takes the mouse), and a drag starts only after a few pixels so clicks still work. Only the top left pane has the sidebar toggle. A terminal docked below a short pane caps its height with the view's (`maxBottomHeight`), and header controls that cost width hide in a narrow pane (`@max-[420px]:hidden`) while their shortcut and palette command stay. The panes are not saved across restarts (only the selected session is).

## Collapsible sections and the queue

Every sidebar section but Needs you closes from its header (`SectionHeader` with `toggle.leading`: the chevron always shows in the gutter, `faint` (`muted` on hover and focus) whatever the section's tone, and turns 90° when open; `data-section-toggle`). Closed, Archived is docked under the list (`data-archived-dock`), outside the scroll area, so a short list never scrolls; opened, its header slides into the list right under the last active row (`data-archived-header`, FLIP) and the list scrolls it near the top only when it lands below the middle (`archivedRevealTop`). A closed header keeps its count and a summary in the state's colour (`headerSummary`: "2 unread" in `unread`, the Queue's "1 ready" in `ok`). A queued item that is ready has a light `ok` tint and an `ok` inset ring (`QUEUE_SURFACE`) with a primary Start; waiting items show a clock and what they wait for, with a secondary Start on hover. The queue's menu and keys (`useQueueMenu`) are shared by the sidebar and Home.

## Pipelines

A pipeline's sub-sessions (#179, docs/pipelines.md) nest under their parent in the open sidebar, which is a `role="tree"`: session rows are `treeitem`s with `aria-level`, `aria-posinset` and `aria-setsize` (the list is virtualised, so there are no nested groups), and each row's wrapper has `data-list-row`. A parent is closed by default; its chevron or ← → (`sidebar.section-toggle`) opens and closes it, and selecting a sub-session opens its parent. The parent takes the most urgent state of its own, its children's and its run's (`sidebarTree` in the protocol, `state/pipelineTree.ts`), and its second line is the run's progress with the pipeline icon (lucide `ListTree` in the `pipeline` token, never a state colour). The rail and `sidebarGroups` list parents and run rows only. A run row (a run started from New session) is a pane keyed by its run id (`isRunRowId`, `RunRowPane`), like a remote session; `localSessionId` is null for it. The parent's step tree, a step's read-only line and its round sit above the conversation's scroll area, like the catch-up banner; the finished-step rows and the verdict card come after it. Pure words and rules for these views are in `state/pipelines.ts` and `components/pipelines/runView.ts`.

## Unsent messages

A draft is marked with an 11px pen (`PencilLine`, `text-faint`, never a status colour) in the row's corner after the pin and before the age; on an icon or button (the rail, the + button) it is a `PenBadge` (`components/drafts/`). Its text shows as `Draft:` (muted) and the start of it in italics at `text-text/80`, only where no status line (needs you, working) takes the place. Drafts live in `state/draftsStore.ts` (keys: a session id, or `newDraftKey(root)` for New session); anything that lists them uses `useUnsent()`, and opening one goes through `openDraft`.

## Saved prompts

In `components/savedPrompts/`, the format in `packages/protocol/src/savedPrompts.ts`. A prompt's blanks are written in its text (`{{name}}`, `{{name:type}}`, `{{name?}}`, `\{{` for braces); `parse`, `fill`, `missing` and `toPlainText` are the only readers, and the box and the editor work on `Segments` (text runs with a blank between each two, `fillModel.ts`). In the message box (`PromptFiller`) the text runs are `contentEditable="plaintext-only"` spans out of the Tab order and each blank is a chip: an `<input>` for text, a `role="combobox"` for the rest, whose `BlankPopover` (a portal, `data-popover`) never holds the focus and gives it back on Esc. An empty chip has a dashed `accent-ink` border, a filled one the `edge` border; the scope tag is muted (every project), `accent-ink` with a person (just for you) or `link` with people (shared). The prompt being filled is part of the draft (`Draft.fill`). Global and personal prompts are in `saved_prompts`, shared ones under `prompts` in `.seshboard.json`, read and written through `actions/sharedFile.ts` (keys and indent kept), with their use counts in `shared_prompt_uses`, never in the file. Smoke hooks: `data-saved-prompt-header`, `data-blank`, `data-blank-empty`, `data-saved-prompts-settings`.

## New session's layout

New session uses the width: where on the left (the projects), what in the middle (the message box), and what's around it on the right (`newSession/newSessionLayout.ts`). The view is an `@container/new-session`, so the sidebar and side panels count. The layouts go by the content's width, the view less its padding (40px a side, 24px under a 780px view):

| Content | Layout | Columns |
|---|---|---|
| 1120px and up | Three (`data-new-session-layout="three"`) | Left and right 280px, growing to 320px at 1540; the centre takes the rest; a 32px gap |
| 780px to 1120px | Two (`two`) | Left 280px, the centre takes the rest; the right column's content moves under the box |
| Under 780px | Stacked (`stack`) | One column, as the view scrolls |

The content stops growing at 1540px (a 1920 window with a 300px sidebar) and centres in the view after. `newSessionLayout(contentWidth)` says the layout and columns for what code needs: how many projects to show, and which section the context leaves out. `NEW_SESSION_GRID` is the same thing in CSS. A container query only sees the view, so its breakpoints are the content's plus the padding (860px and 1200px); a test keeps them in step.

The markup is the same in every layout, so the message box keeps its text and focus through a resize. In columns the page never scrolls (`@min-[860px]/new-session:overflow-hidden`): the project list and the context scroll on their own. The box is at least 210px at rest in three columns and 140px in two. It grows with the text up to the room its column has, then scrolls inside, through a chain of shrinking flex columns (`large` on `Composer`). In two columns the context keeps at least 120px. Its `/`, `@` and `#` lists open on the side of the box with more room (`paletteRoom`), since the box sits high in the view.

The three columns are landmarks: an `aside` labelled Projects (`data-new-session-projects`), the `main` with the box, and an `aside` labelled About this project (`data-new-session-context`). The app's outer `main` gives up its role while New session shows, so a page has one. Another computer's New session (`RemoteNewSession`) keeps one column, up to 56rem (`NEW_SESSION_COLUMN`).

**The projects** (`FolderPicker`): the Run on switch full width, Find a project (⌘F, the filter field opens in its place), the rows, "All N projects…" and Add project…, then Quick question as a dashed row. In columns the rows are one column of quiet lines, as many as fit up to 9 (`projectsThatFit`). Stacked, they are two columns of 8, and one of 6 under 400px (`ROW_GRID`). Picking one changes the route tray and the context, and leaves the focus where it was: a row takes no focus on a click, and a pick from the filter field puts it in the box.

**The focus limit** (`focus/FocusLine.tsx`): one line above the box, in a polite live region that stays on the page, so reaching the limit is announced. While at the limit, Start reads Add to queue on ⌘↩, and Start anyway is in its menu in Nudge and left out in Strict (`atFocusLimit` in `startMenu.ts`). A quick question, a pipeline, a queued item or a schedule that is open, and a provider without the queue keep their own Start, and go through the gate as before. What counts is in the context; stacked, the line's Show opens it under the line.

**The context** (`NewSessionContext`, `sessionContext.ts`): In <project> (`contextRows`: what `pickUpRows` lists, then the last 3 done, each with its state and age), Going now (only with a focus limit; not when stacked), and Defaults for <project>. `contextSections` leaves out a section with nothing in it. A click opens a session.

## Project rows

Projects are rows (`newSession/ProjectRow.tsx`, shared by New session, another computer's `RemoteNewSession` and Home): the icon at 30px, the whole name over the state and branch, and the ⌘ key faint on the right (hidden from screen readers, in `aria-keyshortcuts`). On Home and another computer they are a grid in a container query on the list, not the window: one column, two from 520px, three from 780px (`PROJECT_GRID`, `COLUMN_BREAKPOINTS`); `useColumns` reads the same breakpoints so the code knows how many rows to show (`quickCount`: 6, 8 or 9) and where the arrow keys go (`gridMove`). A name that doesn't fit is cut in the middle (`useMiddleEllipsis`, measured on resize only), and the tooltip has the whole name and folder. Projects on another computer show two letters (`projectInitials`) and no monitor badge, since the Run on switch above says where.

## Home

Home uses the window's width instead of a centred column, the same as New session so nothing jumps between them: up to 1620px (`HOME_WIDTH` in `newSession/newSessionLayout.ts`), centred in the view, 40px in (24px under 780px). It is an `@container`, so its breakpoints follow the view, not the window: three lanes (Needs you, Working, To review) at `0.8fr 1.1fr 1.1fr` from 1200px, two from 760px, one below. Where two lanes or fewer fit, an empty Needs you is left out and the line under the greeting says it. Under the lanes, your projects (New session's `ProjectRow`s, in `PROJECT_GRID`) with Up next on the left, and usage in a `2fr 1fr` column on the right from 1100px; under it below that. Every card is a link to its session. The cards are tinted (`bg-text/6`), except Needs you's, which keeps its pink frame. In the usage column, a profile with sessions today or over half a limit keeps its card with thin bars (`Meter size="compact"`), and the quiet ones share one card, a line each. The selection and wording live in `home/homeModel.ts`.

## Other computers

Sessions of a paired computer (docs/remote-access.md) are rows of the same sidebar (`state/remoteRows.ts`: the same status rules as that computer's own list; an open prompt is needs you), in the same groups and order, through `sidebarGroups` like local ones. A remote row's `id` is `remoteRowId` (`state/remoteSelection.ts`), and a remote session is a pane like a local one: its leaf in the layout is that id, so it opens in the active pane, beside another (⌥-click, Open beside) and by dragging, and `SplitPanes` draws it with `RemotePane`. So `selectedId` and `paneIds` can hold a remote id: code that hands the active pane's session to this computer's engine, hosts or terminal takes it through `localSessionId` (null for a remote one). The `remote` main view is only a computer's page (`useComputers().pageId`). Open a row with `openRow`. Everything on another computer carries the violet marker and nothing else: a `ComputerChip` (`row` size on a row's second line, `header` size in a header and the message box), the badge on its `ProjectIcon` (`remote`), and a 2px `remote` line along the top of its view (an inset shadow). Each computer can have its own colour (Settings › Remote, `COMPUTER_COLORS`: violet by default, or a profile colour's token): put `useComputerTint(computerId)` (or `computerTint(computer.color)`) as the `style` of the root of what belongs to it (its row, its view, a badge), and pass `computerId` to `ComputerChip` where nothing around it has the tint. It sets `--sb-remote` there, so keep using the `remote` utilities, never a profile colour directly. Popovers render outside that root, so their chips take `computerId`. What only works on that computer stays in its place, disabled, with `onlyThereLine` as its tooltip ("Terminal is on mystic. Not available from here."); never hide it, so the layout doesn't jump. Its text is `RemoteText`: nothing in another computer's transcript acts here (no file links, no Run, no images loaded, only http(s) links, never HTML). An offline computer keeps its last list, dimmed to 55%, with `offlineLine`. The sidebar's Computers strip and "Show sessions from" filter by computer, per window (`useComputers().hidden`, `THIS_COMPUTER` for this one).

The Computers strip is one line. Every chip is neutral (`bg-border/45`, as This Mac's), with a paired computer's colour on its name only, its dot for the connection, its needs-you count and, only while Mine is on, a person (`data-computer-scope` on the chip). A click shows only that computer; its menu (Mine or All in a segmented control, what Mine hides, notifications) opens from a ▾ that shows on hover and keyboard focus and comes after the chip in the tab order (`data-computer-menu-button`), a right-click or Shift+F10. Chips never wrap: names are cut at 9rem, the last chip that shows cuts its name down to 3rem (`MIN_NAME`) before it folds, and the chips that still don't fit fold into "+N" (`data-computers-more`), whose menu lists them; `fitComputerChips` decides from copies of the chips at rest measured out of sight, keeping room for one ▾, so a hover never pushes the line over. The rows that filter leaves out are not listed and the sidebar says nothing of them (a row per section was distracting); the chip's menu says how many it hides, and a search still finds them. In All, the name of whoever started someone else's session follows the branch in the `remote` colour.

A computer's page (`ComputerView` with `ComputerOverviewBody`, the `remote` view; Open in Settings › Remote, and its chip when its sessions can't be in the sidebar) is that computer's Home: what needs you, the longest wait as its `ComputerPrompt` card to answer there and the others as rows with Open (one card on the page, so the card's keys belong to one prompt), Working cards, then at most `RECENT_LIMIT` recent sessions by project (`computerOverview.ts`), all through its Mine / All filter, which the page switches too (`data-computer-page-scope`). An offline computer shows its last list at 55% and nothing to answer; an unpaired one, or a pane standing in for one of its sessions, keeps the one line of why.

## Back and forward

The mouse's back and forward buttons step through the places shown (`state/navHistoryStore.ts`). It watches `useSessions` and `useProjectPage`, so a view needs no code to be remembered, only a place in `NavPlace` (`state/navHistory.ts`) when it adds state of its own. Another tab of the same project, page of Settings or active pane changes the current entry instead of adding one, and a place left within 600ms (⌃⇥ walking) gives its entry to the next. A project opened from a Settings page has that page in its breadcrumb (Settings › Memory), which goes back there.

## Settings search

Settings' search finds what is listed in `components/settingsSearch/settingsIndex.ts`: label and line under it as the page shows them, other words people use (`keywords`), and a `target` selector on its page (`fallback` when the target only shows in some states). A new setting gets an entry there; a test fails while a `Toggle` or labelled row on a Settings page has none, and the smoke step opens every entry and checks it lands. A chosen result flashes the closest `[data-setting-row]` (Toggle's label and the pages' row components have it), else its radio group or section.

## Claude Code mods

In `components/mods/`; see [mods.md](mods.md). Whatever a mod draws sits in a `ModFrame`: a 24px header with the puzzle icon and the mod's name (Seshboard's, never the mod's), a 1px `border`, a 10px radius, the body on `card`. A mod's frame never takes a status colour or the permission card's pink. Bands sit under Seshboard's permission cards and above Up next (`promptStack`), at most 160px; panes are right-panel tabs (`mod:<id>` in `RightTab`) with "From <mod> · pane" under the tabs; statuses are chips in the box's row before Ask that give way before anything else in the row moves (`fitModChips`: they fold into "+N", then the prompt shield loses its word and keeps its icon); toasts carry the mod's name (`source`). Show mods off (`showMods`) hides all of it but the prompt shield (`data-mod-shield`), since screening happens in Claude Code. Smoke hooks: `data-mod-frame`, `data-mod-band`, `data-mod-pane`, `data-mod-status`, `data-mods-chip`.

## Charts

The Usage view, `components/usage/charts.tsx`. Series take the `chart-*` tokens (`chart-input`, `chart-output`, `chart-cache-write`, `chart-cache-read`), never status colours; the plan windows' lines reuse them in a fixed order (Weekly `chart-cache-read`, a model's weekly `chart-input`, Session `chart-output`, dashed so it stays apart from Weekly for colour-blind readers). Stacked bars keep the token types in the order they were checked in (uncached input, output, cache write, cache read, from the baseline up). Activity's day strip has its own three, `chart-time`, `chart-turns` and `chart-shipped` (the parts of a day's score in `activityModel.ts`, from the baseline up), the same in every theme because the themes' own `chart-input` and `chart-output` can clash with the fixed two; the days that aren't picked are dimmed, and a day's tooltip is a `TooltipLayer` card with `data-tooltip-rows` (a swatch per row). 2px lines, 4px rounded bar tops, a 2px gap in the card's colour between stacked parts, a quiet `border` grid, text in text colours (never a series colour), a legend from two series, direct labels at a line's end, a hover tooltip (a crosshair on lines), and **Show as table** on every chart (`ChartCard`). Something that comes back at a reset is the `hatched` utility (diagonal stripes in the text colour). Shares of activity are always labelled as estimates. The only money shown is the estimated API cost (`costEstimate.ts` in the protocol: list prices per model, fixed exchange rates; the engine prices tokens per model, as `cost` in US dollars on breakdown rows, buckets and totals, `usage.cost` per plan window and `usage.sessionCost`): after the usage bars, on the Limits cards, in a **Cost (est.)** column and tile of the Usage view, and next to Context under a session's message box. It is always `≈` (`useCostFormat`, in the currency of Settings › Usage, null while Show estimated cost is off) and called an estimate at API prices, never a charge; a cost another computer didn't send stays blank, never zero. Paired computers with `REMOTE_FEATURE_COSTS` answer `usage.sessionCost` (a session there, `RemoteSessionCost`) and `usage.windowCosts` (the plan windows from the starts this computer's plan gave, added up by `useWindowCosts`, which says which computers count).

## Project page and tables

Projects is one view (`components/projects/ProjectsView.tsx`) for both the `projects` and `project` views: `ProjectList` on the left (270px, `bg-sidebar`, like the Settings nav) and the project on the right. ## Context menus and confirmations

Right-click and Shift+F10 open the same `Menu` (`isContextMenuKey` and `contextMenuPoint` in `lib/contextMenu.ts`); an item in another menu that has its own context menu sets `contextMenu` on its `MenuEntry`. After a save or delete that closes a dialog, confirm it with an inline `Notice tone="success"` next to what changed, cleared by `useFlash` (`components/ui/useFlash.ts`). Toasts (`toast()` in `state/toastStore.ts`, bottom right) are for news that isn't next to anything on screen: an Undo after a quick action, a queued item that turned ready. They go by themselves after five seconds (paused on hover and while the window is in the background). Updates to Seshboard and Claude Code are toasts too (`components/updates/UpdateToasts.tsx`, built on `ToastFrame`), but stay until they're dealt with. Anything floated over a terminal sits outside the xterm host, which is `isolate` so xterm's own z-indexed layers can't cover it.

Quick actions on a row (the sidebar's session rows, Settings › Sidebar › Quick actions on hover) are a `toolbar` of 24px icon buttons in a bordered pill on `bg-popover`, floated over the row's right edge (`RowActions.tsx`). They show on hover and on keyboard focus (`group/row` on the row's wrapper, `group-has-[:focus-visible]`), never on touch, and the row's lines only make room for them then, so titles don't jump. Which buttons a row gets is the pure `quickActionsFor` (`sidebar/quickActions.ts`); each runs the same function as its item in the session menu (`useSessionMenu`), then a toast with Undo (`quickUndo.ts`, also ⌘Z in the sidebar). Archive on a working session asks first.
