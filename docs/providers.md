# Providers

Seshboard drives Claude Code. **Providers** are the other agents it works with: GitHub Copilot CLI first ([#199](https://github.com/estruyf/seshboard/issues/199)). A provider is used through a **profile**: Settings › Profiles adds a profile of Claude Code or of another provider, each a config folder with its own login (`CLAUDE_CONFIG_DIR`, `COPILOT_HOME`). Without a profile of it, nothing of a provider is read or run. Its sessions follow Claude Code's rule in the sidebar: those started outside Seshboard show when the sidebar shows sessions from other apps (**Settings › Sidebar**). They show up with the provider's mark on the row and in the header, in search, catch-up and on the phone, and their transcript opens like any other. A provider with a **driver** (Copilot has one) can also start sessions from New session and continue them from the message box; one without is read-only. Claude Code's own actions (fork, rewind, Ask, rename, delete, plan usage) never apply to them. **Signing in is the provider's own**: Seshboard never handles its credentials.

## How it fits together

| Piece | Where | What it does |
|---|---|---|
| Ids and names | `packages/protocol/src/providerConstants.ts` | `SESSION_PROVIDERS`, `OPTIONAL_PROVIDERS`, `PROVIDER_NAMES`, and `otherProviderOf` / `isOtherProviderSession` for a `SessionSummary` (whose `provider` is missing for Claude Code's). |
| The adapter | `packages/engine/src/providers/provider.ts` | `ProviderAdapter`: the provider's folder, how its files map to sessions (`ProviderFiles`), its `SessionSource`, and the command that resumes a session in its own CLI. |
| Profiles | `profiles/profileStore.ts` | A profile's `provider` (migration v42; `claude` for every profile from before). `runtimes()` is Claude Code's profiles only, which everything that starts Claude Code uses; `providerProfiles()` the others, with their folders. Settings export and import carry the provider. |
| The registry | `packages/engine/src/providers/registry.ts` | `providerCatalog()`: what each provider is (name, modes, resume command, its own default folder), for Add profile and the message box. `createProvider()`: the adapter for one provider profile. |
| One adapter per profile | `providers/providerProfiles.ts` | `ProviderProfiles` makes an adapter per provider profile and keeps it while its folder stays the same; a removed profile's runtime stops. |
| One source | `providers/providerSources.ts` | `ProviderSources` puts Claude Code's profiles and the provider profiles behind one `SessionSource`, and routes each session to the profile that listed it (its `profileId`). Fork, rename and subagents stay Claude Code's. |
| The index | `sessions/sessionIndex.ts` | A provider profile's folder is one more root, with its `ProviderFiles` and its `profileId`: watched and scanned like a Claude profile's `projects/`, with none of Claude Code's format read for it. |
| Guards | `engine.ts` (`assertClaudeSession`), `HostManager.startHost` | Refuse Claude-only actions with `READ_ONLY_SESSION`. `startHost` covers every way to a session's process (message box, phone, Up next, schedules). Read-only sessions are also left out of the archive clean-up. |
| UI | `apps/ui/src/components/providers/` | `ProviderMark` (each provider's icon in `PROVIDER_ICONS`; Copilot's is `CopilotIcon`) on rows and in the header, `ReadOnlyNotice` in place of the message box (with the resume command from the adapter), `ProvidersSettings`; `state/providersStore.ts` holds the snapshot. |

Each reader turns its provider's records into the messages Seshboard reads from Claude Code (`RawSessionMessage`, with Claude-style `text`, `thinking`, `tool_use` and `tool_result` blocks). Tools with a Claude Code counterpart are renamed and reshaped to it (a shell call to `Bash`, an edit to `Edit`, a file read to `Read`), so the transcript shows them with the same cards and diffs. Everything else gets the generic tool card.

## Adding a provider

1. Add its id to `SESSION_PROVIDERS` and `OPTIONAL_PROVIDERS`, and its name to `PROVIDER_NAMES` (`providerConstants.ts`). TypeScript then points at the two places that need it: `PROVIDER_ICONS` in `ProviderMark.tsx`, and the registry.
2. Write its adapter in `packages/engine/src/providers/<id>/`: a `SessionSource` (list, info, messages), its `ProviderFiles`, and a pure converter to `RawSessionMessage` with tests next to it. Use real temporary folders in the tests, with records copied from the agent's own files.
3. Add it to `providerCatalog()` and `createProvider()` in `registry.ts`. Its profiles then work like Copilot's: Add profile offers it, and its adapter gets the profile's folder.
4. Add its entry to `settingsIndex.ts` (`data-provider-<id>` is the toggle's hook) and a line to `CHANGELOG.md`.

Read through the agent's own API where it has one that only reads. Parse its files where it doesn't, and degrade quietly: a missing or changed field leaves a session with less (no title, the folder from another record), never an error. Never write to the agent's folder.

## GitHub Copilot CLI

- **Where:** `$COPILOT_HOME/session-state`, else `~/.copilot/session-state`; one folder per session, named by its id.
- **What is read:** `workspace.yaml` (title, folder, branch, client, dates; flat YAML, read by `workspaceYaml.ts`) and `events.jsonl` (the conversation; its records have the Copilot SDK's `SessionEvent` shape). Only sessions with an `events.jsonl` and a prompt are listed: the Copilot desktop app keeps other folders there too, and Copilot opens some sessions for itself that never get a prompt.
- **Why not the SDK:** `@github/copilot-sdk` lists sessions (without their titles), but reads a session's events only by resuming it in a runtime, which writes to the session and clashes with a terminal that has it open. Driving sessions later will go through the SDK.
- **Last activity:** the last prompt, reply or tool result in the last 64 KB of `events.jsonl` (resuming or closing a session doesn't count), else `updated_at`.
- **Origin:** `client_name` `github/cli` is the CLI, `vscode` an editor; anything else is unknown.
- **Left out of the transcript:** `report_intent` (Copilot's own status line) and the steps of subagents (events with a `parentToolCallId`), as Claude Code's subagents are left out of the main conversation.
- **Resume:** `copilot --resume=<id>`.

## Driving sessions

A provider can have a **`driver`** (`ProviderDriver` in `provider.ts`): it starts or resumes a session in a folder, sends messages, stops a turn, switches models and answers permission requests. What a running session reports goes through `DriverEvents`, in the shapes Claude Code's sessions use (`HostEvents`): stream deltas, complete `RawSessionMessage`s (from the same converter as the reader, so the live transcript and the file agree), the turn's state, and permission requests for the permission card.

**Signing in is the provider's own.** Seshboard never asks for, stores or passes a credential. Copilot's driver runs the user's own `copilot` (found like `claude`, `copilotBinary.ts`) through the Copilot SDK, with no token, so `copilot` uses its own login (`/login` in Copilot CLI, or the GitHub CLI's). When it isn't signed in, `status()` says how to sign in with Copilot CLI. The SDK's bundled runtime and `koffi` (only used to host that runtime in-process) are not shipped (`electron-builder.yml`).

Copilot's driver (`copilot/copilotDriver.ts`):
- One headless `copilot` runtime for all sessions, started on first use and stopped with the engine.
- Sessions it starts are recorded by Copilot with `client_name: seshboard`, which the reader reads as started in Seshboard (origin `app`).
- Events: `copilotLive.ts`. Permission requests and answers: `copilotPermissions.ts` (shell → Bash, write → Edit with its diff, read → Read, url → WebFetch, MCP → `mcp__server__tool`; Always allow is Copilot's approve for the session).
- **Modes** (`COPILOT_MODES`): Seshboard's Ask before edits, Accept edits, Plan mode and Auto mode (shown as **Autopilot**), mapped to Copilot's agent modes (interactive, plan, autopilot) through `session.rpc.mode.set`. Accept edits and Autopilot approve Copilot's file reads and writes in Seshboard (`approvesItself`); commands still ask.
- **Steering:** a message sent with `steer` goes to Copilot with `mode: 'immediate'`.
- **Usage:** `session.usage_info` gives the context (`currentTokens` of `tokenLimit`), `assistant.usage` each call's `cost` in premium requests, summed for the session.
- **Not written to disk:** `session.idle` and the other ephemeral events. On disk, a turn that ends on a reply without tool calls is the end of the work (`liveStatusOf`).
- **Permission requests** come to the handler without their id: Seshboard gives each one its own.
- Tests fake the SDK (`CreateCopilotClient`). The live tests are opt-in and cost a few small requests: `SESHBOARD_LIVE_COPILOT_CWD=/path/to/throwaway/repo npx vitest run copilot.live providerHosts.live` (`SESHBOARD_LIVE_COPILOT_MODEL` picks the model).

**Hosts:** `ProviderHosts` (`providers/providerHosts.ts`) runs drivers' sessions next to `HostManager`, which stays Claude Code's. Each reports what a Claude Code host does through the same handlers (`hostEvents` in `engine.ts`): `session.host` info, streams, live messages, permission cards and turn ends, so the transcript, catch-up, pipelines and notifications treat both alike. The engine routes `session.create` (with `provider`), `send` (resuming a session started elsewhere), `interrupt`, `setModel`, `respond` and `close` for a provider's sessions to it; Claude Code's own actions (fork, rewind, Ask, rename, delete) still refuse them. `providers.status` and `providers.models` ask the driver. The driver runs `copilot` with `COPILOT_HOME` set to the folder Seshboard reads, so what it writes is what the sidebar shows.

**The UI:** the profile picks the provider. In New session, a provider profile (the project's, or one picked in the profile chip, which shows the provider's mark) leaves only that provider's models (`providers.models`), greys out the worktree and branch choices, and blocks Start with the provider's own message until `providers.status` says it can run (`useProviderReadiness`, per profile). `createParamsFor` sends only the folder, the message, the model, the mode and the `profileId`; the engine's `createSession` starts the profile's provider. Settings › Profiles adds a provider profile (Runs with, its own folder offered), shows its account from `providers.status`, and its **Sign in** runs the provider's own sign in in the window's terminal (`providers.signIn`: `COPILOT_HOME=<folder> copilot login`). A terminal for a provider profile gets its folder (`profileEnv`). A provider's session gets the message box with `ProviderSessionControls` (its model, switchable while it runs here) and none of Claude Code's chips, Ask, Tools, Send now or plan usage; `ReadOnlyNotice` is left for providers without a driver. Host info carries `provider`, so a session started a moment ago is known before it is indexed.

**Routing:** `RoutedHostManager` (`providers/routedHosts.ts`) is the engine's `hosts`: Claude Code's `HostManager`, with the session-level methods (send, interrupt, respond, mode, model, Up next, list, close) routed to `ProviderHosts` for a provider's sessions. Every way to a session (the message box, the phone, Up next, schedules, usage limits, project actions, pipelines) goes through them, so each reaches a provider's sessions without knowing about providers. `HostManager.startHost` still refuses a provider's session, in case anything goes around them.

**Parity:**
- **Modes:** the driver's `modes` (`ProviderInfo.modes`) are what the mode chip, New session and ⇧Tab offer, in the provider's words. A mode picked while the session isn't running is kept (`sessionSettings`, shared with Claude Code's) for the next resume, as is the model.
- **Up next:** `ProviderHosts` keeps a queue like `SessionHost`'s, in the same `UpNextStore`: queued messages go one per turn, `steer` joins the turn, Send now stops it and goes first, Stop or a failed turn holds the queue, and a restart brings it back held.
- **Usage:** host info carries the context (`contextTokens`, `contextMax`) for the context meter, and `providerUsage` (Copilot's premium requests) for the footer. Claude Code's plan usage and limits don't apply.
- **Open in its own app:** `ProviderAdapter.inUse` and `live`. Copilot marks a session it has open with `inuse.<pid>.lock`; Seshboard's own `copilot` holds one too, so only an alive process that isn't Seshboard's counts (`copilotInUse.ts`). The engine polls `live` for sessions active in the last day and adds them to the live list, so the sidebar shows them working or waiting; sending to one is refused (`SESSION_BUSY_ELSEWHERE`) until its own app lets go.
- **The phone:** `RemoteSession.provider` hides Claude Code's model, effort and mode chips and Ask about this session; sending, Stop, permission cards and Up next work through the routing. `options.get`'s profiles carry their `provider`; picking a provider profile in New session's Options asks `providers.ready` for it (its install or sign-in message, and its models) and leaves only its model and modes; `session.create` with that `profileId` starts it.
- **Slash commands:** `DriverSession.commands()` (and the driver's, before a session runs) fill the message box's `/` list (`providers.commands` in New session). A message that starts with one of them runs it: Copilot's `session.commands.invoke` (`copilotCommands.ts`) gives a prompt to send as a turn, words to show (a note in the conversation, and the session goes idle), or a model to switch to; results that need Copilot's terminal UI say what to do instead. Copilot's commands that Seshboard's controls already are (model, plan, autopilot, permissions, allow-all, rename) are left out. **Compact** on the context meter sends `/compact` this way.
- **Tools:** `DriverSession.capabilities()` and `mcp()`: Copilot's MCP servers (on, off, reconnect), its agents and its own skills (not its built-in ones), through `session.capabilities` and `session.mcp`.
