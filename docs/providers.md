# Providers

Seshboard drives Claude Code. **Providers** are the other agents it works with: GitHub Copilot CLI ([#199](https://github.com/estruyf/seshboard/issues/199)) and OpenAI Codex CLI ([#276](https://github.com/estruyf/seshboard/issues/276), read-only for now). A provider is used through a **profile**: Settings › Profiles adds a profile of Claude Code or of another provider, each a config folder with its own login (`CLAUDE_CONFIG_DIR`, `COPILOT_HOME`, `CODEX_HOME`). Without a profile of it, nothing of a provider is read or run. Its sessions follow Claude Code's rule in the sidebar: those started outside Seshboard show when the sidebar shows sessions from other apps (**Settings › Sidebar**). They show up with the provider's mark on the row and in the header, in search, catch-up and on the phone, and their transcript opens like any other. A provider with a **driver** (Copilot has one) can also start sessions from New session and continue them from the message box; one without (Codex, for now) is read-only. Claude Code's own actions apply to them only where the provider has them (`supports`): Copilot forks, rewinds, renames, deletes and sets effort through its own APIs; Ask about this session and plan usage stay Claude Code's. **Signing in is the provider's own**: Seshboard never handles its credentials.

## How it fits together

| Piece | Where | What it does |
|---|---|---|
| Ids and names | `packages/protocol/src/providerConstants.ts` | `SESSION_PROVIDERS`, `OPTIONAL_PROVIDERS`, `PROVIDER_NAMES`, and `otherProviderOf` / `isOtherProviderSession` for a `SessionSummary` (whose `provider` is missing for Claude Code's). |
| The adapter | `packages/engine/src/providers/provider.ts` | `ProviderAdapter`: the provider's folder, how its files map to sessions (`ProviderFiles`), its `SessionSource`, and the command that resumes a session in its own CLI. |
| Profiles | `profiles/profileStore.ts` | A profile's `provider` (migration v42; `claude` for every profile from before). `runtimes()` is Claude Code's profiles only, which everything that starts Claude Code uses; `providerProfiles()` the others, with their folders. Settings export and import carry the provider. |
| The registry | `packages/engine/src/providers/registry.ts` | `providerCatalog()`: what each provider is (name, modes, resume command, its own default folder), for Add profile and the message box. `createProvider()`: the adapter for one provider profile. |
| One adapter per profile | `providers/providerProfiles.ts` | `ProviderProfiles` makes an adapter per provider profile and keeps it while its folder stays the same; a removed profile's runtime stops. |
| One source | `providers/providerSources.ts` | `ProviderSources` puts Claude Code's profiles and the provider profiles behind one `SessionSource`, and routes each session to the profile that listed it (its `profileId`). Fork and rename go to the provider's source when it has them (Copilot's); subagents stay Claude Code's. |
| The index | `sessions/sessionIndex.ts` | A provider profile's folder is one more root, with its `ProviderFiles` and its `profileId`: watched and scanned like a Claude profile's `projects/`, with none of Claude Code's format read for it. |
| Guards | `engine.ts` (`assertClaudeSession`), `HostManager.startHost` | Refuse Claude Code's actions with `READ_ONLY_SESSION`, except those the session's provider has (`supports`). `startHost` covers every way to a session's process (message box, phone, Up next, schedules). A provider's sessions are in the archive clean-up only when it can delete them. |
| UI | `apps/ui/src/components/providers/` | `ProviderMark` (each provider's icon in `PROVIDER_ICONS`: `CopilotIcon`, `CodexIcon`; the phone has its own in `apps/remote`) on rows and in the header, `startableProfiles` (`startable.ts`), which keeps a read-only provider's profiles out of everything that starts a session (the profile chip, a project's profile, the default, triggers, pipeline steps), `ReadOnlyNotice` in place of the message box (with the resume command from the adapter), `ProvidersSettings`; `state/providersStore.ts` holds the snapshot. |

Each reader turns its provider's records into the messages Seshboard reads from Claude Code (`RawSessionMessage`, with Claude-style `text`, `thinking`, `tool_use` and `tool_result` blocks). Tools with a Claude Code counterpart are renamed and reshaped to it (a shell call to `Bash`, an edit to `Edit`, a file read to `Read`), so the transcript shows them with the same cards and diffs. Everything else gets the generic tool card.

## Adding a provider

1. Add its id to `SESSION_PROVIDERS` and `OPTIONAL_PROVIDERS`, and its names to `PROVIDER_NAMES` and `PROVIDER_SHORT_NAMES` (`providerConstants.ts`). TypeScript then points at the two places that need it: `PROVIDER_ICONS` in `ProviderMark.tsx`, and the registry.
2. Write its adapter in `packages/engine/src/providers/<id>/`: a `SessionSource` (list, info, messages), its `ProviderFiles`, and a pure converter to `RawSessionMessage` with tests next to it. Use real temporary folders in the tests, with records copied from the agent's own files.
3. Add it to `providerCatalog()` and `createProvider()` in `registry.ts`, with its `installCommand` and its capability list, `supports`: which of Claude Code's own features (`PROVIDER_FEATURES`: fork, rewind, rename, delete, effort, Ask, worktrees, branches, pipelines, the queue, schedules, triggers) it has. The rest stay off for its profiles: New session turns them off with a notice and a "Not with <provider> yet" tooltip (`switchLosses`, `notWithYet`), and its session's ⋯ menu ends with one faint line that names the session actions it doesn't have yet (`claudeOnlyLine`). The list grows as it gets them. Its profiles then work like Copilot's: Add profile offers it, and its adapter gets the profile's folder.
4. Give `detectProvider()` what it needs (it uses `files()` and the driver's `status()`, or the adapter's own `status()` for a provider without a driver, so a provider with both gets the offer in Settings › Profiles), and add a line to `CHANGELOG.md`. Set `homeEnv` (`{ COPILOT_HOME: home }`): a terminal of the profile and its Sign in run the CLI with it. Anything the adapter runs to read (Codex's app-server) stops in its `dispose()`.

Read through the agent's own API where it has one that only reads. Parse its files where it doesn't, and degrade quietly: a missing or changed field leaves a session with less (no title, the folder from another record), never an error. Never write to the agent's folder.

## GitHub Copilot CLI

- **Where:** `$COPILOT_HOME/session-state`, else `~/.copilot/session-state`; one folder per session, named by its id.
- **What is read:** `workspace.yaml` (title, folder, branch, client, dates; flat YAML, read by `workspaceYaml.ts`) and `events.jsonl` (the conversation; its records have the Copilot SDK's `SessionEvent` shape). Only sessions with an `events.jsonl` and a prompt are listed: the Copilot desktop app keeps other folders there too, and Copilot opens some sessions for itself that never get a prompt.
- **Through the SDK where it can:** while the profile's `copilot` runtime runs, a session's events are read with `sessions.readPersistedEvents` (which doesn't resume it) and open sessions are found with `sessions.checkInUse`, so a change to Copilot's files needs no change here. The runtime isn't started just to read: before it runs, `events.jsonl` and the `inuse.<pid>.lock` files are read instead, and a read that fails (an expired cursor) falls back to the file. The list stays on the files: the SDK lists sessions without their titles.
- **Last activity:** the last prompt, reply or tool result in the last 64 KB of `events.jsonl` (resuming or closing a session doesn't count), else `updated_at`.
- **Origin:** `client_name` `github/cli` is the CLI, `vscode` an editor; anything else is unknown.
- **Left out of the transcript:** `report_intent` (Copilot's own status line) and the steps of subagents (events with a `parentToolCallId`), as Claude Code's subagents are left out of the main conversation.
- **Resume:** `copilot --resume=<id>`.

## OpenAI Codex CLI

Read-only for now ([#276](https://github.com/estruyf/seshboard/issues/276), Phase 1): no driver, `canStart: false`, `supports: ['delete']`.

- **Where:** `$CODEX_HOME`, else `~/.codex`. Codex keeps a rollout file per session in `sessions/YYYY/MM/DD/rollout-<timestamp>-<thread id>.jsonl` (`.jsonl.zst` once Codex compressed it) and moves archived ones to `archived_sessions/`.
- **What is read:** nothing from those files. `codexSource.ts` asks `codex app-server` (one per profile, with its `CODEX_HOME`, started on the first request and stopped when idle), through its stable methods only: `thread/list` for the list (every page, every source but subagents, never archived, never `useStateDbOnly`, so a trashed rollout drops out), `thread/read` when a file changes, `thread/turns/list` with `itemsView: "full"` for the conversation (the default `summary` view leaves out every tool call). Since Codex 0.167 a thread's history is in `thread_history_1.sqlite` and old rollouts are compressed, so the API is the only complete reader. Reading needs no sign in.
- **Watching:** Codex still appends to the rollout file on each turn, so a change under `sessions/` is what asks for the thread again (`codexFiles.ts`).
- **Not every refresh:** the index lists every 2 minutes, longer than the server's idle stop. While no rollout file changed (their names, sizes and times), the last list answers, asked again at least every 10 minutes (a name set elsewhere touches no rollout). The `codex` found is kept until a start says it's gone.
- **Fails quietly:** a Codex that isn't installed, or a server that crashed or timed out, keeps the last list (none before the first) and logs once until it works again. A conversation that can't be read throws, so the transcript says so instead of showing nothing.
- **Origin:** `originator` `seshboard` is the app (none yet: there is no driver), source `cli` the CLI, `vscode` an editor; anything else is unknown.
- **Left out:** subagent threads (a `parentThreadId`) and ephemeral ones, as Claude Code's subagents are left out of the list. A subagent opens from its parent's Agent card (`subagent`).
- **Status and sign in:** the adapter's own `status()`: `codex` found (`findCodex`) and `account/read` (a ChatGPT login by its email, an API key without a name). Signed out is no `problem`: reading needs no login. `auth.json` is never read. Sign in runs `CODEX_HOME=<folder> codex login`.
- **Delete:** the thread's rollout files (both spellings, and one in `archived_sessions/`) go to the Trash with `{ codexHome }`; main checks each again (`isTrashableCodexSession`). Not yet refused while Codex CLI has it open: `inUse` and `live` wait for its lock format.
- **Resume:** `codex resume <id>`, shown in place of the message box (`ReadOnlyNotice`).
- **No driver yet:** New session, the queue, schedules, triggers, pipelines, the phone and other computers don't offer its profiles (`readOnly` on the remote hub's profiles), a phone shows the resume command in place of the box (`RemoteSession.readOnly`), Add profile skips the sign in, and its profile has no Default or New session defaults. Starting and continuing sessions is Phase 2 of #276.

## Driving sessions

A provider can have a **`driver`** (`ProviderDriver` in `provider.ts`): it starts or resumes a session in a folder, sends messages, stops a turn, switches models and answers permission requests. What a running session reports goes through `DriverEvents`, in the shapes Claude Code's sessions use (`HostEvents`): stream deltas, complete `RawSessionMessage`s (from the same converter as the reader, so the live transcript and the file agree), the turn's state, and permission requests for the permission card.

**Signing in is the provider's own.** Seshboard never asks for, stores or passes a credential. Copilot's driver runs the user's own `copilot` (found like `claude`, `copilotBinary.ts`; on Windows, npm's install leaves only a `copilot.cmd`, which the SDK can't start, so `npmCopilot` runs its package's script with the user's own `node`) through the Copilot SDK, with no token, so `copilot` uses its own login (`/login` in Copilot CLI, or the GitHub CLI's). When it isn't signed in, `status()` says how to sign in with Copilot CLI. The SDK's bundled runtime and `koffi` (only used to host that runtime in-process) are not shipped (`electron-builder.yml`).

Copilot's driver (`copilot/copilotDriver.ts`):
- One headless `copilot` runtime for all sessions, started on first use and stopped with the engine.
- Sessions it starts are recorded by Copilot with `client_name: seshboard`, which the reader reads as started in Seshboard (origin `app`).
- Events: `copilotLive.ts`. Permission requests and answers: `copilotPermissions.ts` (shell → Bash, write → Edit with its diff, read → Read, url → WebFetch, MCP → `mcp__server__tool`; Always allow is Copilot's approve for the session).
- **Modes** (`COPILOT_MODES`): Seshboard's Ask before edits, Accept edits, Plan mode and Auto mode, named as Claude Code's, mapped to Copilot's agent modes (interactive, plan, autopilot) through `session.rpc.mode.set`. Seshboard answers some requests itself (`approvesItself`): Accept edits approves Copilot's file reads and writes, and Auto mode approves every request (Copilot's autopilot with all permissions, what Copilot CLI recommends for it). Requests already waiting when the mode changes are answered by the new mode.
- **Steering:** a message sent with `steer` goes to Copilot with `mode: 'immediate'`.
- **Usage:** `session.usage_info` gives the context (`currentTokens` of `tokenLimit`), `assistant.usage` each call's `cost` in premium requests, summed for the session.
- **Not written to disk:** `session.idle` and the other ephemeral events. On disk, a turn that ends on a reply without tool calls is the end of the work (`liveStatusOf`).
- **Permission requests** come to the handler without their id: Seshboard gives each one its own.
- Tests fake the SDK (`CreateCopilotClient`). The live tests are opt-in and cost a few small requests: `SESHBOARD_LIVE_COPILOT_CWD=/path/to/throwaway/repo npx vitest run copilot.live providerHosts.live` (`SESHBOARD_LIVE_COPILOT_MODEL` picks the model).

**Hosts:** `ProviderHosts` (`providers/providerHosts.ts`) runs drivers' sessions next to `HostManager`, which stays Claude Code's. Each reports what a Claude Code host does through the same handlers (`hostEvents` in `engine.ts`): `session.host` info, streams, live messages, permission cards and turn ends, so the transcript, catch-up, pipelines and notifications treat both alike. The engine routes `session.create` (with `provider`), `send` (resuming a session started elsewhere), `interrupt`, `setModel`, `respond` and `close` for a provider's sessions to it; Claude Code's own actions refuse them unless the provider has them (Session actions, below); Ask about this session always does. `providers.status` and `providers.models` ask the driver. The driver runs `copilot` with `COPILOT_HOME` set to the folder Seshboard reads, so what it writes is what the sidebar shows.

**Found on this computer:** `providers.detect` asks each provider's CLI about its own folder (`~/.copilot`) without a profile of it: installed and its version, the folder and how many sessions it holds, signed in and as whom. It makes a throwaway adapter for that folder (`detectProvider` in `registry.ts`), asks the same `status()` a profile's runtime does, then stops it. The engine keeps the answer for the run; `refresh` (Add profile's Check again) asks again. Settings › Profiles shows the offer (`ProviderOffer`, `data-provider-offer`) when the CLI is installed, no profile uses the provider and it wasn't put away with Not now (`providerOffersDismissed` in the preferences, per provider; `shouldOffer` in `profiles/providerOffer.ts`).

**Adding a profile** takes two screens: which tool runs its sessions (`data-new-profile-tool`, from `providers.detect`, with the install command and Check again when the CLI is missing), then its name, colour and folder. For the provider's own folder, signed in already, there is no sign in; otherwise Add and sign in runs it in the terminal. A provider profile ends on its ready screen (`ProviderReady`, `data-profile-ready`): who it is signed in as (asked until the sign in is done), how many sessions now show, and Start a session (`useProjects.startWith`), Use for a project (`projects.setProfile`) and Make it the default.

**Premium requests:** `providers.quota` returns a profile's premium requests this period (the driver's optional `quota()`; Copilot's `account.getQuota`, which never hands Seshboard a token). New session's usage line and a session's footer show it in place of Claude Code's plan usage (`ProviderUsage`), and the Usage view shows it for a provider profile (`ProviderUsagePanel`, Phase 5 of #199): what is left, what was used of what, and when it resets, without Claude Code's tabs, periods and plan usage. Profiles there show their tool's logo in their colour, as in the message box.

**The demo** (`npm run smoke:demo`, the screenshots) runs a made-up Copilot CLI, `demoCopilot()`, with `SESHBOARD_STUB_COPILOT=1`: installed, signed in as `demo-user`, with two models and premium requests, and no process behind it. Starting a session with it refuses, so a smoke run never reaches a real Copilot.

**The UI:** the profile picks the provider. In New session, a provider profile (the project's, or one picked in the profile chip, which shows the provider's mark) leaves only that provider's models (`providers.models`), greys out what the provider doesn't have yet (`supports`: for Copilot, Run as a pipeline), and blocks Start with the provider's own message until `providers.status` says it can run (`useProviderReadiness`, per profile). `createParamsFor` sends the same worktree, branch and pull request as for Claude Code, with the provider's model, effort and mode; the engine's `createSession` runs the git steps, then starts the profile's provider. New session's profile menu groups profiles by tool (`byTool`, a header per tool once there are two) and ends with Add profile…. Switching to a provider profile keeps the prompt and attachments, and says what it turned off that was on, with Back to the profile before (`switchNoticeFor` in `newSession/providerSwitch.ts`, `data-provider-switch-notice`); the hint under the box offers to make the profile the project's (`data-use-profile-for-project`). A provider session's ⋯ menu is `providerEntries` in `MoreMenu.tsx`: Compact, Tools, Copy the last reply, Open in its CLI (`providers.openInCli`, refused while Seshboard runs it) and Archive. Settings › Profiles shows a provider profile's account from `providers.status`, and its **Sign in** runs the provider's own sign in in the window's terminal (`providers.signIn`: `COPILOT_HOME=<folder> copilot login`). A terminal for a provider profile gets its folder (`profileEnv`). A provider's session gets the message box with `ProviderSessionControls` (its model, switchable while it runs here) and none of Claude Code's chips, Ask, Send now or plan usage; `ReadOnlyNotice` is left for providers without a driver. Host info carries `provider`, so a session started a moment ago is known before it is indexed.

**Session actions** (Phase 2 of #199): each through Copilot's own API, switched on in `providerCatalog()`'s `supports` (`fork`, `rewind`, `rename`, `delete`, `effort`), which the UI reads (the message toolbar, the ⋯ menu, the sidebar's menu, F2 and ⌘⌫, `sessionCan` in `state/sessionFeatures.ts`).
- **Fork, and Edit and resend:** `sessions.fork` with `toEventId`. Seshboard's message ids are Copilot's event ids, but Copilot keeps the events *before* `toEventId` where Seshboard's fork keeps the message itself: `forkBoundary` (`copilot/copilotActions.ts`) names the event after it, past the results of the tools it asked for, so a fork never starts on a call without its answer. Edit and resend forks at the message before your prompt, as for Claude Code.
- **Rewind:** `session.history` (`listRewindPoints`, `previewRewind`, `rewind` with `conversation-and-files`). Unlike Claude Code's, Copilot's rewind takes the conversation back too: the dialog says so, the message goes back in the box, and the transcript is read again (the hub sends a replace when it gets shorter). It needs Copilot's file-change tracking, which the driver turns on for every session it starts or resumes (`enableFileChangeTracking`; a resume can't restore earlier untracked turns); without it, the dialog says Copilot didn't keep the changes. A session that isn't running is resumed here first; one mid-turn waits.
- **Rename:** `session.name.set`, so Copilot CLI shows the name too. A session not running here is resumed only for that and let go (`renameSession`), and refused while Copilot CLI has it open.
- **Delete, and the archive clean-up:** the session's whole folder (`<COPILOT_HOME>/session-state/<id>`) goes to the Trash, never deleted outright. The engine names it with `{ copilotHome }`, and main checks it again (`isTrashableCopilotSession` in `trashGuard.ts`: a real folder directly in `session-state`, named like a session). Refused while Copilot CLI has the session open; one running in Seshboard is stopped first.
- **Effort:** `setModel(model, { reasoningEffort })`, for models that say they take it (`supportsEffort`), at the levels they list (`ModelOption.efforts`, from `supportedReasoningEfforts`). Copilot's Auto has none until it picks a model; another model starts on its own default.
- **Background tasks:** `session.tasks.list` when Copilot says they changed (`session.background_tasks_changed`) and when a turn ends: the running ones in the background (`executionMode: background`, or a `detached` shell) show in the pill and the panel as `local_bash` or `local_agent`, and Stop is `session.tasks.cancel`.

**The queue, schedules and triggers** (Phase 3 of #199): a queued item, a schedule's run and a triggered session start through `createSession`, which sends a provider profile's to `createProviderSession` (its model, effort and mode). New session saves the provider's own choices with them (`laterDraft`), and opening one puts them back in the provider's chips. Start's ▾ offers Add to queue, Schedule… and Start when… for a provider that has `later`, `schedule` and `trigger` (`startButtonState`'s `provider`). The trigger editor follows the profile's provider: its models and modes, with A pipeline off (and anything else the provider doesn't have). A run's title is set through the running session (`renameSession` in `engine.ts`), never by resuming it a second time.

**Worktrees and branches at start** (Phase 3 of #199): `createSession` runs the same git steps for every profile, before the session starts: it checks out a branch or a pull request, or makes the worktree. Claude Code makes its own `fresh` and `head` worktrees (`--worktree`); for another provider Seshboard makes those too (`makeWorktree` in `git/worktreeFrom.ts`: the same `.claude/worktrees/<name>` folder, `worktree-<name>` branch and `.worktreeinclude` copies), and the session starts in the worktree. The project's setup actions run before its first message (`beforeFirstMessage` in `ProviderHosts.create`), as for Claude Code. The engine refuses a worktree or a branch for a provider without `worktree` or `branch`.

**New session on another computer** (Phase 3 of #199): `RemoteNewSession` does what the phone does. A profile there with a `provider` (from `options.get`) asks that computer's `providers.ready` (in `COMPUTER_METHODS`) for whether it can run and its models, offers only the provider's modes, blocks Start with its message until then, and sends its model and mode with `session.create` (`remoteProviderCreate`), plus a worktree or a branch when that computer's provider has them. The phone sends those too now.

**Pipelines** (Phase 3 of #199): a step can say which tool runs it (`PipelineClaudeStep.provider`; left out: Claude Code), picked in the step's **Runs with** once a profile of that provider exists, with its models (of its first profile) and its own modes. The run itself, its worktree and its Push stay as they are, and New session's Run as stays Claude Code's (a Copilot profile has no `pipeline`). The runner hands the step's provider to `create` and `fork` (`StepSettings.provider`); the engine starts it with the provider's first profile (`stepProviderProfile`) through `createProviderSession`. A fork keeps its tool (`pipelineIssues` refuses a fork of another tool's step): a Copilot step forks a Copilot step through Copilot's fork, then sends the prompt (`forkProviderStep`). A read-only step is a read-only host (`ProviderHosts.create`'s `readOnly`, and `readOnly` for a resume): each permission request is answered at once with `isReadOnlyTool`, the rule of Claude Code's read-only hook, and Accept edits and Auto mode approve nothing else by themselves. The verdict comes from the step's last reply, as for Claude Code. Copilot has no ExitPlanMode, so Approve the plan for me is Claude Code's: a Copilot step in plan mode ends when its turn does.

**Session linking** (Phase 4 of #199): `ProviderHosts` takes the same `links` as `HostManager` (`hostLinks` in `engine.ts`): `warm` before a message is created or sent, `expand` as it goes to the provider, so `@` links carry their briefs and attached issues into a Copilot session too. A slash command goes as typed. The transcript shows the briefs as chips, as for Claude Code (`parseBriefs` reads any user message).

**Files from the box and VS Code** (Phase 4 of #199): the message box (and the VS Code companion's chips in it) writes files as one line of `@` mentions, which Claude Code opens itself. Copilot's driver adds them to the message as Copilot's own attachments (`mentionAttachments` in `copilot/copilotAttachments.ts`): a file, a folder, or a range of lines as a `selection` with its text. The message keeps its mention line, so the transcript and Edit read it back as chips. Text chips (a selection, diagnostics) go as fenced text, as for Claude Code.

**Subagents** (Phase 4 of #199): Copilot writes a subagent's steps in the session's own events, with the `task` call that started it as their `parentToolCallId`. The main conversation leaves them out; `transcript.subagent` for a provider's session asks the adapter (`ProviderAdapter.subagent`, Copilot's `copilotSubagent`), which converts only that agent's events and names it from `subagent.started`. The provider's ⋯ menu has Agents.

**Ask about this session** (Phase 4 of #199): `RoutedHostManager.askAbout` sends a provider's session to `ProviderHosts.askAbout`, which asks the driver (`ProviderDriver.ask`). Copilot's forks the session (`sessions.fork`), registers the fork as ephemeral before it runs (`ProviderSources` leaves ephemeral ids out, so it never shows in the sidebar), resumes it with the read-only rule of Claude Code's Ask (`isReadOnlyTool`), streams the answer, then disconnects and deletes the fork (`client.deleteSession`: Seshboard's own throwaway, as Claude Code's is never written; a session of yours always goes to the Trash). Its premium requests count on the account's quota; the answer records no Claude Code tokens. The phone offers Ask when that computer's provider has `ask` (`sessionCan` in the remote app's `lib/options.ts`).

**Slash command answers** (Phase 4 of #199): a Copilot command that answers in words shows your command and its answer in the conversation, but Copilot doesn't write them to its file. The driver marks those lines `keep` (`DriverEvents.messages`), `ProviderHosts` hands them to `keepNotes`, and `ProviderNotes` keeps them in `provider_notes` (migration v43, kept on a rebuild). `ProviderSources.messages` puts them back after the last message from before each (`mergeNotes`), so a reload shows them where they were. Deleting the session forgets them.

**Routing:** `RoutedHostManager` (`providers/routedHosts.ts`) is the engine's `hosts`: Claude Code's `HostManager`, with the session-level methods (send, interrupt, respond, mode, model, Up next, list, close) routed to `ProviderHosts` for a provider's sessions. Every way to a session (the message box, the phone, Up next, schedules, usage limits, project actions, pipelines) goes through them, so each reaches a provider's sessions without knowing about providers. `HostManager.startHost` still refuses a provider's session, in case anything goes around them.

**Parity:**
- **Modes:** the driver's `modes` (`ProviderInfo.modes`) are what the mode chip, New session and ⇧Tab offer, in the provider's words. A mode picked while the session isn't running is kept (`sessionSettings`, shared with Claude Code's) for the next resume, as is the model.
- **Up next:** `ProviderHosts` keeps a queue like `SessionHost`'s, in the same `UpNextStore`: queued messages go one per turn, `steer` joins the turn, Send now stops it and goes first, Stop or a failed turn holds the queue, and a restart brings it back held.
- **Usage:** host info carries the context (`contextTokens`, `contextMax`) for the context meter, and `providerUsage` (Copilot's premium requests) for the footer. Claude Code's plan usage and limits don't apply.
- **Open in its own app:** `ProviderAdapter.inUse` and `live`. Copilot marks a session it has open with `inuse.<pid>.lock`; Seshboard's own `copilot` holds one too, so only an alive process that isn't Seshboard's counts (`copilotInUse.ts`). The engine polls `live` for sessions active in the last day and adds them to the live list, so the sidebar shows them working or waiting; sending to one is refused (`SESSION_BUSY_ELSEWHERE`) until its own app lets go.
- **The phone:** `RemoteSession.provider` hides Claude Code's model, effort and mode chips and Ask about this session; sending, Stop, permission cards and Up next work through the routing. `options.get`'s profiles carry their `provider`; picking a provider profile in New session's Options asks `providers.ready` for it (its install or sign-in message, and its models) and leaves only its model and modes; `session.create` with that `profileId` starts it.
- **Slash commands:** `DriverSession.commands()` (and the driver's, before a session runs) fill the message box's `/` list (`providers.commands` in New session). A message that starts with one of them runs it: Copilot's `session.commands.invoke` (`copilotCommands.ts`) gives a prompt to send as a turn, words to show (a note in the conversation, and the session goes idle), or a model to switch to; results that need Copilot's terminal UI say what to do instead. Copilot's commands that Seshboard's controls already are (model, plan, autopilot, permissions, allow-all, rename) are left out. **Compact** on the context meter sends `/compact` this way.
- **Tools:** `DriverSession.capabilities()` and `mcp()`: Copilot's MCP servers (on, off, reconnect), its agents and its own skills (not its built-in ones), through `session.capabilities` and `session.mcp`.
